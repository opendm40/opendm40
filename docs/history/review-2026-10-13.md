# fw-rs code review: uncommitted changes, 2026-10-13

Scope: the working-tree diff against HEAD (3e7507c) for `bt.rs`, `gen.rs`, `scope.rs`,
`touch.rs`, `ui.rs`, `app.rs`, `stockfont.rs`, plus the new files `stockfont_data.rs`,
`tools/mkstockfont.py`, `logger.rs` and the `hy3131.rs` additions. Another agent was editing
`main.rs`, `scpi.rs`, `clock.rs`, `startup.rs`, `link.x`, `wdt.rs`, `power.rs`, `build.sh` and
`Cargo.toml` at the same time, so this review does not cover them. I only looked at them where
a reviewed file depends on them (the logger hook-up and `can_draw` in `main.rs`).

Method: I read the code and traced execution paths by hand. I ran `cargo build --release` into a
separate target dir (`/tmp/fwrs-review-target`). The default build has no errors and 59
warnings. `--features embedded-fonts` compiles, but linking fails with or without `native`
(see L8). I re-ran `mkstockfont.py` against `dm40_v_2_6.dec.bin` into a temporary copy. Nothing
was run on hardware, and no source file was changed.

Severity: **H** = data loss, a broken core function, or a reachable panic. **M** = wrong
behaviour a user will hit. **L** = minor, cosmetic or cleanup. Confidence is about whether the
mechanism is real, as traced in the code. It is not a hardware test.

## High

### H1. Logging stops all `App::tick` housekeeping; auto power-off then fires as soon as logging ends
- **Where:** `app.rs:403` (`if !can_draw { return; }`) together with `main.rs`
  `can_draw = usb_up && now >= draw_hold_until && !logging`. The housekeeping skipped is at
  `app.rs:429-466`: `power.poll`, `persist`, the relay re-assert, idle dim/off, and the PD6
  power key.
- **What:** before this change, `can_draw` was false only for a moment during a screenshot.
  Now it is false for the whole logging session. `tick()` returns before any housekeeping, so
  during logging:
  - the PD6 power key does nothing. Holding it for 1.5 s does not power off, and the
    double-press lock does not toggle.
  - the battery is not polled. `power.bars` freezes, and so do the BT cmd-09 battery bits.
  - settings are not persisted.
  - `last_input` keeps aging. Only `gesture()` sets it (`app.rs:853`), touch is suspended while
    logging, and host traffic never updates it.
- **Failure scenario:** with the default `off_idx = 1` (30 min), the host logs for more than
  30 min, then sends `LOG:STAT OFF` (or the mode/range guard auto-stops the logger). On the
  next loop `can_draw` is true again, `idle > OFF_MS` holds, and `power_off()` runs
  immediately. The ring buffer still holds up to 2048 records the host has not read yet
  ("Captured data stays readable"). Those records and the USB link are lost. The same thing
  happens to a host that uses only SCPI without logging (that part was already there).
- **Fix:** move the `!can_draw` early return so it only skips drawing (status bar, chart).
  `power.poll`, `persist`, PD6 and the idle timers should keep running. Separately, refresh
  `last_input` on USBTMC/BT host traffic, or at least while `logger.active()`, so a
  host-driven session never counts as idle. Leave the relay re-assert gated during logging: it
  blocks 10 ms.
- **Severity:** H. **Confidence:** high.

### H2. STOP replaces the frozen trace with a different capture (untriggered or partial) and can change the timebase
- **Where:** `scope.rs:376-392` (`apply`, which calls `stop()` and then runs the clamp loop),
  `scope.rs:424-447` (`stop`; the snapshot is the `if was_busy` block at 438), `snapshot_linear` at `scope.rs:467`,
  `snapshot_roll` at `scope.rs:477`, and the stopped branch of `poll` at `scope.rs:556-566`.
- **What:** `poll()` starts the next acquisition straight after returning a frame, so when the
  user presses STOP an acquisition is nearly always in flight. `apply(run=false)` calls
  `stop()`, which turns that in-flight record into the stored record:
  - If it has finished (NDTR = 0), it is a newer record than the one on screen. Its anchor is
    `len/2` and its trigger is `None` (the trigger search in `poll` never ran on it). The trace
    jumps to an untriggered window.
  - In Normal mode the in-flight record is usually one that `poll` would have discarded (no
    trigger). The triggered event the user stopped on is replaced by a flat or untriggered
    trace within 250 ms (`zoom_pending` is set, then `zoom_frame`).
  - If it is partial (slow timebases, where a record takes 0.1-10 s), `stored_len = rec - NDTR`.
    The clamp loop in `apply` (`while zoom_screen(tb) > stored_len { tb -= 1 }`) then lowers the
    user's timebase. Worked example: at 1 s/div (tb 24, fs 2500, rec 25800, about 10 s), STOP
    pressed 2 s into a record gives len ≈ 5000, and the loop lands on tb 22 (200 ms/div). At
    100 ms/div, STOP 300 ms in gives len ≈ 7500 and tb drops to 19 (20 ms/div). Roll mode works
    the same way: STOP 60 s into a 50 s/div roll (3000 samples) gives tb 26 (5 s/div).
  - At HEAD, a stopped scope returned `None` from `poll`, so the last drawn frame stayed on
    screen unchanged. This is a regression in the scope's most basic workflow ("freeze what I
    see").
- **Fix:** the displayed frame's samples are already being overwritten in BUF by the next
  acquisition, so a stop requested by the user must not snapshot the in-flight record blindly.
  Options, simplest first:
  - (a) In `stop()` called from `apply(run=false)`, keep the snapshot only if the record is
    complete (NDTR == 0). Then run the same `find_trigger` window as `poll` and anchor on the
    trigger. In Normal mode, reject it if there is no trigger. Otherwise set
    `stored_valid = false` and leave the screen frozen, as before. Never clamp `tb` on the STOP
    press itself, only on a later timebase change.
  - (b) Don't start the next acquisition until the previous frame has been drawn. Defer
    honouring `run=false` until the in-flight frame completes.
  - (c) Double-buffer when `rec <= CAP/2`. That covers every Auto/Normal timebase with
    tb ≤ 10 (≤ 20 µs/div, rec ≤ 10800).
- **Severity:** H (data the user explicitly froze is replaced). **Confidence:** high.

## Medium

### M1. `snap_freq` returning 0 is not idempotent: the "silent" state becomes 1 Hz, and the frequency setting is lost
- **Where:** `gen.rs:75-89` (non-square above 50 kHz returns `0`), `gen.rs:142` (`apply`
  snaps again), callers `app.rs:577`, `app.rs:1248`, `app.rs:1328` (SCPI `FREQ`), and persist
  at `app.rs:598` / `app.rs:627`.
- **What:** `snap_freq(w, 0)` takes the `f < 1000` branch and returns `0.max(1) = 1`. The
  keypad (`app.rs:577`), the wave-cycle tap (`app.rs:1248`) and SCPI `FREQ` (`app.rs:1328`)
  all snap first and then call `gen.apply()`, which snaps again, so they never reach the
  documented "0 Hz, silent" state: they land on 1 Hz. The only caller that reaches `apply`
  with an unsnapped frequency is SCPI `FUNC` (it changes only `g.wave`). That path gives a
  transient 0 (silent), which becomes 1 Hz on the next `apply`.
- **Failure scenarios:**
  1. Power on (new default Square at 2 MHz) and tap the wave box once. The handler snaps
     (Triangle, 2 MHz) to 0, then `apply` snaps 0 to 1, so the generator is at **1 Hz** after
     one tap, never silent. Cycling on through Ramp, Sine and back to Square keeps 1 Hz. The
     2 MHz setting is gone for good.
  2. Sine via SCPI `FUNC SIN` from the 2 MHz default gives `freq_hz = 0`. Any later `apply`
     (`OUTP ON`, a VOLT change, the generator ON key) gives `snap(Sine, 0) = 1`, and the
     output switches on at 1 Hz instead of staying silent.
  3. `persist_words` saves 0 and `restore` clamps it to 1, so after a reboot the generator is
     at 1 Hz.
  4. Keypad entry of e.g. 100 kHz on a Sine: `kp_apply` snaps to 0, then `apply` snaps to 1.
     The UI shows 1 Hz.
  At HEAD, the same inputs gave a working 50 kHz output.
- **Fix:** keep the requested frequency in `Settings` and compute an "effective output Hz" in
  `apply` (0 means silent). Or make `snap_freq` leave 0 as 0 and stop the callers
  double-snapping. If silent is really the stock behaviour, show "--" or "0 Hz" in the UI and
  keep the user's number for when they switch back to Square.
- **Severity:** M. **Confidence:** high.

### M2. Stopped records are re-rendered with the *current* range and probe, so volts and measurements are wrong after a V/div change
- **Where:** `scope.rs:556-566` (stopped re-render every 250 ms), `zoom_frame` at
  `scope.rs:673`. The volts mapping is `Scope::volts` / `row_of_code`, and `scope_meas::compute`
  uses `sc.s.range`.
- **What:** the stored record is raw ADC codes. The record keeps `stored_fs` but not the range,
  AC/DC setting, or probe it was captured with. Changing V/div while stopped switches the
  front-end relays and re-maps the old codes with the new range's gain (`XR[r]/(g0-g1)`). At
  HEAD nothing was re-rendered while stopped, so this could not happen.
- **Failure scenario:** capture a 1 Vpp signal at 1 V/div and press STOP. Change to 2 V/div:
  the trace is redrawn as if the codes were taken at 2 V/div. The display reads about 2 Vpp,
  and `Vpp`/`RMS`/`Mean` in the measurement row are wrong by the gain ratio. A failed AUTO-set
  that restores `saved.run = false` shows the autoset's last capture (range 9 or similar) with
  the user's range.
- **Fix:** store `range`, `probe` (and `ac`) with the record. While stopped, convert codes with
  the stored gain, which turns a V/div change into a digital vertical zoom. The alternative is
  to refuse range changes while stopped.
- **Severity:** M. **Confidence:** high.

### M3. Logger pacing gate is measured from the last *attempt*, which adds up to ~0.8 P of jitter and drops conversions when the loop is slow
- **Where:** `logger.rs:202-218` (`last_attempt_us` is updated even when `ad1_ready()` is false).
- **What:** after a failed INTF check the next check waits another 0.8 × nominal. A conversion
  that lands just after a failed check is seen up to about 0.8 P late. With the loop
  quantization (loop period L) included, the spacing between checks is `ceil(0.8P/L)·L`. When
  that is greater than P (for example L ≈ 0.6-1.0 × P, which is 250-417 µs at OSR 2048), the
  observation phase drifts by `spacing - P` per sample until a conversion is overwritten
  unread. Plain "poll INTF every loop" would never lose a sample while L < P. The timestamps
  also carry this extra jitter, so the "constant interval" claim is weaker than it needs to be.
- **Fix:** gate from the last *successful* sample: `now - last_sample_us >= 0.8·nominal`, then
  check INTF on every loop until it is ready. Or drop the gate: one INTF read is about 45 µs.
- **Severity:** M. **Confidence:** medium. The mechanism is certain; how often it bites depends
  on the real loop time while logging, which I did not measure.

### M4. The logger's constant interval is broken by USB-disk writes (SPI-flash erase 45-400 ms)
- **Where:** `main.rs` loop order (`msc.poll(&mut disk)` runs every iteration, before
  `logger.poll()`), `spiflash.rs:12,152-179` (a 4 KiB erase stalls the main loop for 45-400 ms,
  and a block write is an erase plus 16 page programs).
- **What:** any host write to the mass-storage disk during a logging session stalls the loop
  for up to 400 ms. At OSR 2048 that is up to about 960 conversions lost per erase. They are
  counted in `missed` and visible as timestamp gaps, so nothing is lost silently (FR-38 is
  met), but the host OS can trigger these writes without the user doing anything (atime,
  journal, desktop indexers).
- **Fix:** while `logger.active()`, have the MSC answer writes with NOT READY / busy (SCSI
  sense 02/04/xx) or defer them. At least document in `LOG:PREamble?`/TODO that disk writes
  void the interval.
- **Severity:** M. **Confidence:** high (from the spiflash code; not measured).

### M5. Single mode at 2-50 s/div is a silent linear capture of up to ~9 minutes
- **Where:** `scope.rs:420` (`rec = CAP` for Single) and `scope.rs:530` (Single never rolls).
- **What:** with Roll on, `apply` allows tb up to 29. Single at tb 25..29 captures 26624
  samples linearly at 1250..50 S/s, which takes 21 s to 532 s. Nothing is drawn until the DMA
  finishes. The status label shows "T'D" the whole time, and the only way out is to press
  STOP, which then hits H2. At HEAD, TB_MAX = 23 and Single used `screen + WIN`.
- **Fix:** cap Single at `TB_YT_MAX` (as Auto/Normal are capped when Roll is off), or let Single
  roll and stop at the trigger or a full record.
- **Severity:** M/L. **Confidence:** high.

## Low

### L1. hv_warning erase punches a 27 × 64 px hole into the compact scope graph
- `app.rs:293` resets `hv_shown` only in the `View::Dmm` arm of `draw_static`. If you go
  Dmm (≥ 100 V, so `hv_shown = true`) and then swipe to DmmScope, the first reading computes
  `hv = false`, which differs from `hv_shown`, so `ui::hv_warning(false)` (`app.rs:782`)
  fills `rect(0,80,40,64)` with BG. That rectangle now lies inside the compact scope area
  (`SCOPE_COMPACT.y0 = 78`, previously 134, so the overlap grew from 10 rows to 64). The
  per-column cache does not repaint the hole until those columns change.
- Fix: set `self.hv_shown = false` in the `View::DmmScope` arm too.
- Confidence: high. This existed before, but the new layout makes it much worse.

### L2. Logger starts sampling inside the DMM's 450 ms settle window
- `main.rs` `LOG:STAT ON` calls `app.dmm.start()` (which switches relays, writes the config and
  sets `deadline = now + 450`), then `logger.start()` right away. `logger.poll` ignores the
  settle deadline, so the first ~1000 samples (at OSR 2048) can be relay/filter transients and
  nothing marks them.
- Fix: `logger.start(..., settle_until)` should discard samples, or flag them in the preamble.
- Confidence: high on the mechanism; medium on whether it matters for DC inputs.

### L3. `measured_hz()` is wrong after 71.6 min
- `logger.rs:148-157`: `first_ts_us` / `last_ts_us` are u32 µs, so `span` wraps after 2^32 µs.
  Keep `now_us` (u64) for the first and last sample. The 32-bit wire timestamp is fine as long
  as the host unwraps it; say so in the preamble docs.

### L4. BT one-shot AT init runs regardless of link state and blocks ~150 ms
- `bt.rs:231-254`. It runs on every power-on (the stock does this once ever). If a phone is
  already connected (`power.bt_connected()`, PC14), the module is in transparent mode. In that
  case "AT+SBNDM40x\r\n" probably reaches the phone app as data, `at_answer` swallows 50 ms of
  incoming request frames, and `AT+RESET` drops the link. That depends on the module, so
  confidence is low. It also blocks the main loop for 150 ms. In `main.rs` it is not gated by
  `!logging`, so turning BT on during a logging session puts a 150 ms gap into the log.
- Fix: run it only when `!power.bt_connected()` and `!logging`.

### L5. The BT cmd-09 flag bits are guesses
- `bt.rs:320-327`: bit 6 = lock and bit 3 = charging are marked "name guess" / "meaning guess"
  in the header. The phone app might show a lock or charge icon at the wrong time. Before this
  change the byte was `hold|rel|5`. Check against the stock app before relying on it.

### L6. Stopped scope keeps recomputing static data in every view
- `scope.rs:556-566` returns a zoom frame every 250 ms whenever `stored_valid`, even when the
  scope is not powered or not visible. `app.scope_poll` then re-downsamples `wave` and runs
  `scope_meas::compute` over up to 25000 samples every 300 ms, even on the DMM or Gen pages.
  At HEAD a stopped scope cost nothing.
- Fix: emit only on `zoom_pending` (set it from `App::draw_static` when entering a scope view)
  instead of on a timer.

### L7. Smaller cleanups and simplifications
- `scope.rs:592-599`: `poll` masks `BUF[..n]` with 0x3FF again right after `stop()` →
  `snapshot_mark` already did it (`scope.rs:457`). That is a redundant 25.8 K-sample pass per
  slow frame; drop the loop in `poll`.
- `snapshot_roll` does `rotate_left` on the full 52 KB BUF on every `apply` while rolling (each
  trigger-level drag event, `app.rs` `Gesture::Drag` → `scope_set`). That is acceptable but
  pointless when `run` stays true; snapshot only when `!s.run`.
- `app.rs:297` repeats the full-panel `fill_rect` that `DmmView::draw_static(.., true)`
  (`ui.rs:230`) just did. That is about 120 K pixels, a few ms per redraw.
- `app.rs:1004-1005`: the comment says "MENU still exits to the back view", but key 0 on
  Device goes to Settings (`app.rs:928`). Fix the comment.
- `app.rs:1226/1230`: unused `steps`/`plus` (compiler warning, pre-existing). The unreachable
  pattern warnings at `app.rs:1082/1111` are pre-existing scope-menu arms, not from this diff.
- `ui.rs:604` `eng()` has no `k`/`M` prefixes. With the new 2 MHz default, the scope top-bar
  `gen_state` shows "GEN Squ 2000000Hz" in a 136 px F14 box, which is at or past the edge.
  Add k/M scaling for values ≥ 1e3.
- Device page: "Hardware" is printed as `V<maj>.0` with a made-up `.0` minor (`app.rs`
  `fmt_ver(.., bd(0x10), 0)`).
- `ui.rs` `CELLS_C[4]` (the OL row) is 154 px wide in a 152 px rect. That is harmless (the last
  cell is a blank and the unit starts at x 198), but the doc comment admits it. Shrink the last
  cell to 18.

### L8. `embedded-fonts` does not link in any current layout (info)
- `cargo build --release --features embedded-fonts` fails with ".text overflowed CODE by 91956
  bytes / FLASH by 75740". Adding `native` gives the same result, because the native layout is
  not in `link.x` yet. Cargo.toml labels the feature "future", so this is not a defect in these
  files, but until the native linker script exists nothing builds or tests this path.

## Checked and found correct

These looked worth worrying about, but hold up:

- **touch.rs, 0x5A path byte-identical.** `write_at` uses `ok = ok && tx(b)`, so the Goodix
  probe on this unit is one START, the 0x28 address byte NAK'd, and a STOP. `read_reg_at`
  short-circuits before the read. After that, the Hynitron init and frame traffic (D1 01 /
  D204 read 4 / D1 09; D000 read 7, AB check, extra-point reads, D0 00 AB) match HEAD exactly.
  `poll` behaves the same: when INT is high it flushes `pending`; a bad frame returns `None`
  without touching `pending`; `code` is still computed from `p.x` with the same thresholds. The
  Goodix-only `due ||` term short-circuits on `ctrl == Hynitron`.
- **touch.rs Goodix bounds.** `n = status & 0x0F` (≤ 15): extra-point reads are capped at 5,
  the key register `0x814F + 8n` cannot overflow u16, the key bit is masked to 4 bits, so
  `1 << code` stays ≤ 8. There is no panic path.
- **stockfont default path unchanged.** `Glyph::alpha`, `valid`, `line_h`, `descent` and
  `glyph` moved into `mod data` verbatim.
- **stockfont_data.rs is reproducible.** Re-running `mkstockfont.py` on
  `dm40_v_2_6.dec.bin` (into a temp copy) gives a byte-identical file. All 19 `Font(0x…)`
  addresses used anywhere in `src/` appear in `font_data()`. None of them uses the
  `VT_BPLUS` class that the generator accepts but the flash path rejects. All are VT_A or
  VT_B, so the two paths accept the same fonts. Blob spans are `ceil(w·h·bpp/8)`, so
  `alpha()` indexing stays in bounds.
- **gen.rs.** `apply`'s `freq_hz == 0` guard does prevent the `÷0` in `dac()`. For f ≥ 100 kHz
  the PWM `find` always succeeds (no fallback). Square 50-100 kHz snaps to 50 kHz and goes to
  the DAC path (f > 5000: `n = 200`), not PWM.
- **scope.rs bounds with `rec = CAP`.** In `poll`: `win = WIN.min(n - screen)` with
  screen ≤ 25000 < CAP, `half + win ≤ n`, `start + screen ≤ n`. In `zoom_frame`:
  `want ∈ [2, stored_len]`, `start ≤ stored_len - want`. `snapshot_mark` refuses len < 2, so
  `stored_len - 1` cannot underflow. In `snapshot_roll`, `wr < CAP` and `rotate_left(wr)` is
  valid.
- **`zoom_screen` u64 → usize truncation.** `(screen·stored_fs/fs_tb) as usize` truncates
  mod 2^32 on thumbv7. I enumerated all 27 × 27 (stored tb, view tb) pairs: 30 pairs exceed
  2^32, and none of them truncates to a value ≤ CAP, so the clamp loop and `zoom_frame` are
  unaffected. The comment "exact integer" is still misleading; a `.min(usize::MAX as u64)`
  saturation would make the safety explicit.
- **Timebase tables for tb 25..29.** HW has 1250/500/250/125/50 Hz entries (TIM1 PSC 7..199,
  ARR 19999). Roll is clamped to 3..29, YT to 3..24, and `restore` sets `scope.roll` before
  `apply`. The Roll toggle calls `apply` afterwards, so tb is re-clamped.
- **Back navigation.** Device → Settings → Menu → `back_view`. `show()` does not overwrite
  `back_view` while moving between menu pages (Device was added to both lists). Swipes are
  disabled on Device. Analog power is left alone on Device.
- **Settings geometry.** The last row ends at y 44 + 7·34 + 31 = 313 < 320. `settings_hit`
  rejects taps in the 3 px gaps. The title-bar back (y < 40) cannot collide with row 0 (y ≥ 44).
  Rows 0-6 keep their old indices, and Device is index 7 (it used to be "Back").
- **Compact DMM+scope layout.** The value is at y 24-54, unit and mode at 23-55, scope labels
  at y0-19 = 59-76, the graph at 78-277, and the buttons start at BTN_Y 280. Nothing overlaps.
  LETTERS has every glyph that `fmt7` emits (digits, `-`, `.`, `0`, `L`). Nothing else draws
  history or aux in compact mode.
- **HOLD repaint.** `meter.shown()` is still `Some` while held (`update` returns `None`, `shown`
  is unchanged), so the `hold_shown` mismatch path repaints the frozen value with the new
  label, whether the toggle came from the side key or from BT cmd 04.
- **BT.** `dmm.model()` is `.min(2)` at load, so `b'A' + model` cannot overflow.
  `power.bars ≤ 5` fits the 3-bit field.
- **logger.rs.** Ring arithmetic is fine (`len ≤ CAP`, overwrite counted). `encode` fits 511
  records in the 6144 B USBTMC buffer and caps at 9999 B for `#4`. DWT wrap is handled by
  `wrapping_sub` as long as `poll` runs at least every 21 s, which it does every loop.
  `missed` uses `nominal_us.max(1)`, so there is no ÷0. The R22 writes use the stock 0x10 base
  (0x13/0x15/0x17 family). On stop, `dmm.start()` → `set()` resyncs `dmm.r22` (`dmm.rs:372`),
  so the DMM's OSR cache is not left stale.
- **Build.** The default release build has no errors. Warnings in the reviewed files are only
  dead code or unused items.
